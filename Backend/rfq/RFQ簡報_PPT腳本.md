<!-- Page 8: 核心功能 1 - 預先註冊機制 -->
## 核心功能 1: 預先註冊機制

### 🔑 Notification Key 映射

```
外部系統調用:
POST /api/v1/notify
{
  "notifyKey": "project-alpha",  ← 識別專案
  "message": "部署完成",
  "targets": ["all"]             ← all/conversation_id/email
}

系統處理:
1. 驗證 notifyKey 存在且啟用
2. 查詢專案的所有目的地（預先註冊）
3. 展開 targets（all → 所有目的地）
4. 批次發送通知
```

### 優點

✅ **安全可控**: 必須預先註冊目的地，避免濫發  
✅ **集中管理**: IT 管理員統一管理所有目的地  
✅ **權限隔離**: 專案只能發送到自己的目的地  
✅ **審計追蹤**: 完整記錄誰發了什麼訊息到哪裡

## 核心功能 2: Two-loop Enqueue 設計

### 📊 處理流程

```
1️⃣ Producer Loop (API)
   ┌─────────────────────────┐
   │ 接收請求 → 快速寫入 DB   │
   │ 回傳 202 Accepted (1-5ms)│  ← 低延遲
   └─────────────────────────┘

2️⃣ Enqueue Worker (背景)
   ┌─────────────────────────┐
   │ 掃描 pending → 推入 Redis│
   │ 按優先級排序 (high/normal/low)│
   └─────────────────────────┘

3️⃣ Consumer Loop (Actor Pool)
   ┌─────────────────────────┐
   │ BLPOP → Actor 處理       │
   │ 重試機制 + 熔斷器保護    │
   │ 更新狀態 → sent/failed   │
   └─────────────────────────┘
```

### 關鍵優勢

✅ **低延遲**: API 回應時間 < 5ms  
✅ **高吞吐**: 支援 1000+ notifications/min  
✅ **可靠性**: 持久化佇列，防止資料丟失  
✅ **可觀測**: 完整的狀態追蹤

<!-- Page 10: 核心功能 3 - 重試與熔斷器 -->
## 核心功能 3: 智能重試機制

### 🔄 指數退避 + Teams Retry-After

```
重試策略:
├─ 第 1 次失敗: 等待 1 秒
├─ 第 2 次失敗: 等待 2 秒
├─ 第 3 次失敗: 等待 4 秒
├─ 第 4 次失敗: 等待 8 秒
├─ 第 5 次失敗: 等待 16 秒
└─ 最多重試 5 次，之後標記為 failed

特殊處理:
└─ 429 Rate Limit: 讀取 Retry-After header，精確等待
```

### 🔌 熔斷器保護

```
狀態轉換:
Closed (正常) 
  ↓ 連續失敗 5 次
Open (熔斷) - 不調用 API，直接失敗
  ↓ 等待 30 秒
Half-Open (測試)
  ↓ 成功 → Closed | 失敗 → Open
```

**效益**: 防止級聯故障、快速失敗、自動恢復
